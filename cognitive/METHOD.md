# METHOD · 把一本书变成 agent 可执行的规则（六步法）

> **本文件是 `cognitive/` 层所有 skill 的**统一标准**。**
> **每做一本新书，照这个流程走；每做一次，这个文件就更成熟一点。**

---

# 一、⭐ 为什么需要这个方法

**做出 1 个 skill 是"一次性的"。**
**做出"造 skill 的方法"才是**可复用资产**。**

**⭐ 我们要的不是 6 个 skill，是**能把任何一本好书变成 skill 的能力**。**

**⭐⭐ 这和数据层是同一个逻辑：**

| 层 | 产品 | 元层（引擎/方法） |
|---|---|---|
| **数据** | **事实包** | **`build_pack.py`**（换垂直改参数） |
| **知识** | **书 → skill** | ⭐ **本文件（`METHOD.md`）** |

---

# 二、⭐⭐ 六步法（每一步有硬要求）

## 第 1 步 · 读透（不是摘要）

| 项 | 要求 |
|---|---|
| **做什么** | **找出这本书的**核心判断**——作者在主张什么** |
| ⭐ **关键** | **不是"这本书讲了什么"，是"作者**反对什么、主张什么**"** |
| **反例** | ❌ **"《事实》讲了很多数据"（这是摘要，不是核心判断）** |
| ✅ **正例** | **"《事实》主张：人对世界的判断系统性地偏差，必须用数据校正"** |

**⭐ 检验**：**能否用一句话说出"作者在跟谁争论、争什么"？** **说不出 → 没读透。**

## 第 2 步 · ⭐ 分离「道理」与「准则」

| 类别 | 特征 | 处理 |
|---|---|---|
| **道理** | **读时点头，读完就忘** | ⭐ **不写进 skill（或只放 references）** |
| ⭐ **准则** | **能变成"当 X 时，做 Y"** | ⭐ **必须写进 SKILL.md** |

**⭐ 检验**：**这句话能不能翻译成 if-then？** **不能 → 它是道理，不是准则。**

**⚠️ 常见错误**：**把"要客观"这种空话当准则** —— **"要客观"无法执行。**

## 第 3 步 · ⭐ 翻译成 agent 规则

| 要求 | 说明 |
|---|---|
| ⭐ **if-then 形式** | **"当用户给出单个数据点时，先找对比基线，再下结论"** |
| **可检验** | **agent 做完能被验证"有没有照做"** |
| ⛔ **禁止** | **"要专注"· "要客观"· "要有系统思维"**（**这些是口号，不是规则**） |

**⭐ 每条规则必须带**反例**：**「不这么做会怎样」。**

## 第 4 步 · ⭐⭐ 在真实场景验证

| 项 | 要求 |
|---|---|
| **做什么** | **必须有一处真实应用** |
| ⛔ **不接受** | **"理论上应该有用"** |
| ✅ **接受** | **"我们在 X 项目里用了，结果是这样"** |

**⭐⭐ 这一步是我们和"读书笔记"的分水岭：**
> **别人总结书，我们在自己项目里验证。**

## 第 5 步 · ⭐ 记录验证数据（`evidence.md`）

**⭐ 每条证据必须四段式：**

| 段 | 内容 |
|---|---|
| **问题** | **改造前是什么状况（带数字）** |
| **书里哪个概念** | **用了这本书的哪个概念（要具体）** |
| **具体做法** | **做了什么** |
| **量化结果（前 → 后）** | **⭐ 必须有前后对比数字** |

**⭐⭐ 而且必须写**诚实边界**（见 §四）。**

## 第 6 步 · 写成 `SKILL.md`

**⭐ 结构：**

```markdown
---
name: <kebab-case, = 目录名, ≤64>
description: <一句话 + 全部触发条件 + 不适用边界, ≤1024>
---

# <标题>

## When to use
- 具体触发 1
- 具体触发 2
**Not for**: ...

## Rule 1: <规则名>
<一句话：规则是什么、为什么成立>
**Do**: ...
**Don't**: ...

## Output format
<产出格式，短且可检查>

## References
- `references/<book>-book.md`
- `references/evidence.md`  ⭐
```

# 三、⭐⭐ `cognitive/` 层的统一结构

**每个 skill 必须有：**

```
<skill-name>/
├── SKILL.md                    ← 六步法第 6 步
├── references/
│   ├── <book>-book.md          ← 第 1-2 步的产物（我们自己写的理念提炼）
│   └── evidence.md             ← ⭐ 第 4-5 步的产物（项目验证数据）
└── METHOD.md                   ← ⭐ 这本书的**具体**转化记录（不是复制本文件）
```

**⚠️ 注意：每个 skill 的 `METHOD.md` 是**这本书的具体记录**：**
- **这本书读到什么核心判断**
- **哪些是道理、哪些是准则**（第 2 步的分离结果）
- **翻译成了哪几条规则**
- **在哪验证的、数据是多少**
- **⭐ 这本书的转化有什么特别之处（下一本可以借鉴什么）**

**→ 做满 6 本后，本文件（`cognitive/METHOD.md`）升级成正式方法论。**

# 四、⭐⭐ 诚实边界（**不可妥协**）

**每个 `evidence.md` 必须写清四条：**

| # | 边界 |
|---|---|
| **1** | **数据口径**（哪些实测、哪些估算） |
| **2** | ⭐ **归因限制** —— **"先有改造，后有概念归因，不是对照实验"** |
| **3** | ⭐ **引用表述** —— **"本项目的验证案例"，而非"因果证明"** |
| **4** | **未完成项**（**改造还在进行中，就写"进行中"，不写"已达成"**） |

**⭐⭐ 为什么这条最重要：**
> **我们做的整个项目叫"可信数据"。**
> **如果自己的证据不诚实，就没资格谈可信。**
> **⭐ 所以：宁可少写一条证据，不可夸大一毫。**

---

# 五、⭐ 版权边界（**法律风险**）

| ✅ 可以做 | ⛔ 不可以做 |
|---|---|
| **总结理念，写我们自己的理解** | **大段引用原文** |
| **注明「基于《书名》的理念」** | **声称是我们的原创理论** |
| **Apache-2.0 发布我们写的部分** | **把书的原文/PDF 放进来** |
| **翻译成 agent 规则**（这是我们的贡献） | **翻译书中段落**（那是演绎权） |

**⭐ 每个 SKILL.md 的结尾必须有：**
```
*Based on: <book>. We license our translation, not the original.*
*License: Apache-2.0*
```

# 六、⭐⭐⭐ 五本书的体系位置（**这是"star project"的骨架**）

**⭐ 我们的 `cognitive/` 不是 skill 集合，是**一条完整的认知链路**：**

```
① 输入层  《事实》         如何正确看数据
    ↓
② 处理层  《思考，快与慢》  如何不被直觉骗
    ↓
③ 质量层  《噪声》         如何让判断一致
    ↓
④ 全局层  《系统之美》      如何看到系统和反馈
    ↓
⑤ 带宽层  《稀缺》         如何在有限资源下工作
    ↓
⑥ 执行层  《深度工作》      如何产出深度
```

**⭐⭐ `cognitive/README.md` 必须画出这张图。**
**→ 让人一眼看出：这不是 6 个孤立 skill，是一套**操作系统**。**

# 八、⭐⭐ 《事实》的特殊性（**它和我们业务最接近**）

**⭐ 我认为它应该被**优先**做，理由：**

| 理由 | 说明 |
|---|---|
| **1** | ⭐ **主题直接同源**——**"如何正确使用数据"就是我们的业务** |
| **2** | ⭐ **能双向加强** —— **skill 教 agent 用数据；我们的数据平台给它提供数据源** |
| **3** | ⭐⭐ **可以做成"示范性 skill"** —— **skills 调用 MCP 数据，形成完整闭环** |

**⭐⭐⭐ 如果做得好，《事实》的 skill 可以这样调用我们的数据：**
```
用户：「现在全球极端贫困率是多少？」
agent：调用《事实》skill 的规则 → 识别"这是需要基线对比的问题"
      → 调用 Trustbase MCP 的 query_domain_benchmarks
      → 给出带来源、带置信度的答案
```

**→ 这就是"认知 skill + 数据 skill"的闭环。**

**⭐ 这是我最期待的一个。**

# 九、⭐⭐⭐ 可行性办法（**让方法可以被复制的一套工具**）

> **负责人要求**：*"方法论和可行性办法要做好，后续我们可以直接复制整套方式方法。"*
>
> **⭐ 所以这一节不是"再讲一遍流程"，是**把流程变成可执行的工具**。**

## 9.1 ⭐ 四个配套文件（缺一不可）

| # | 文件 | 作用 | 位置 |
|---|---|---|---|
| **1** | ⭐ **`template/BOOK-SELECTION-SCORE.md`** | **选书打分表**（四维打分 + 判定标准 + 红旗） | `template/` |
| **2** | ⭐ **`template/SKILL-TEMPLATE.md`** | **SKILL.md 模板** | `template/` |
| **3** | ⭐ **`template/EVIDENCE-TEMPLATE.md`** | **evidence.md 模板**（含四条诚实边界） | `template/` |
| **4** | ⭐⭐ **`template/BOOK-TO-SKILL-CHECKLIST.md`** | **交付前检查清单 + 评分卡 + 常见错误** | `template/` |

**⭐⭐ 这四个文件 + 本文件 = **完整的可复制方法论包**。**

## 9.2 ⭐⭐ 标准作业流程（SOP · 七步）

```
① 选书      → 用 BOOK-SELECTION-SCORE.md 打分（≥4.0 才做）
② 读透      → 找出核心判断（作者在跟谁争论）
③ 分离      → 道理 vs 准则（能翻译成 if-then 的是准则）
④ 翻译      → 写成 if-then 规则 + 反例
⑤ 验证      → 在真实场景用一次 + 记录前后数据
⑥ 写文件    → SKILL.md + <book>-book.md + evidence.md + METHOD.md
⑦ 检查      → 用 BOOK-TO-SKILL-CHECKLIST.md 逐项打勾 + 评分（≥4.5 才上线）
```

**⭐ 每一步都有对应的**文件**——不靠人记，靠清单。**

## 9.3 ⭐⭐⭐ 复制到新书时的**最小动作**

**⭐ 如果有人要按这个方法做一本新书，他只需要：**

1. **复制 `template/` 到工作目录**
2. **填 `BOOK-SELECTION-SCORE.md`**（打分，≥4.0 才继续）
3. **照 `SKILL-TEMPLATE.md` 写 `SKILL.md`**
4. **照 `EVIDENCE-TEMPLATE.md` 写 `evidence.md`**
5. **按 `BOOK-TO-SKILL-CHECKLIST.md` 逐项检查**
6. **评分 ≥4.5 提交 PR**

**⭐⭐ 这就是"直接复制整套方式方法"的具体形态。**

## 9.4 ⭐⭐ 质量闸门（**三重**）

| 闸门 | 时机 | 判据 |
|---|---|---|
| **闸门 1 · 选书** | 开工前 | **评分 ≥4.0** |
| **闸门 2 · 内容** | 写完 SKILL.md | **规则是 if-then + 有反例** |
| **闸门 3 · 交付** | 提交前 | **检查清单全过 + 评分 ≥4.5** |

**⭐ 任一门不过 → 不进入下一步。**

## 9.5 ⭐⭐⭐ 这本方法论的"元层"价值

**⭐ 和数据层完全同构：**

| 层 | 产品 | ⭐ 元层（引擎/方法） | 可复制性 |
|---|---|---|---|
| **数据** | **事实包**（T-62） | **`build_pack.py`** | ✅ **换垂直改参数** |
| **知识** | **书 → skill** | ⭐ **本文件 + `template/` 四件** | ✅ **换书照 SOP** |

**⭐⭐⭐ 三层都有"引擎"——这才是**方法中枢**，不是数据中枢。**
