# Agent 组织化

## 何时使用

- Agent 数量从 3 个涨到 10 个以上，开始说不清「谁负责什么」
- 出了故障，翻日志才能定位到是哪个 agent
- 两个 agent 在做同一件事，或者互相等对方
- 想加新 agent，但不知道挂在哪里、向谁汇报
- Agent 数量在涨，总产出没涨

**不适用**：

- 只有 1–3 个 agent → 直接写清楚每个的职责就够了，不需要组织结构
- 纯粹的 pipeline（A→B→C 固定流转）→ 那是工作流不是组织，用 DAG 编排
- 需要的是**技术框架**（调度器、消息队列）→ 这是**管理问题**，换框架解决不了

## 一、先诊断：你现在有的是「集合」还是「组织」

**四个判据，中任意一条就说明还是集合：**

| # | 判据 | 检查方法 |
|:-:|---|---|
| 1 | 定义与注册不一致 | 配置文件里的 agent 数 ≠ 运行时数据库里的数 |
| 2 | 有成员没有汇报关系 | 遍历所有 agent，`reports_to` 为空的 |
| 3 | 有成员没有权限边界 | `boundaries` 为空的 = 不知道它能写什么 |
| 4 | 只有运行次数没有产出指标 | 能回答「跑了没」，不能回答「干得好不好」 |

**⭐ 更柝 2026-11-15 的真实诊断结果：**

```
yaml 定义      12 个
DB 注册        21 个      ← 判据 1 命中：差 9 个
缺 reports_to  9 个       ← 判据 2 命中
缺 boundaries  20 个      ← 判据 3 命中（只有 1 个有）
缺 kpi         21 个      ← 判据 4 命中（全部只有 runs/fails 计数）
```

**结论：它有 21 个 agent，但不是组织。**

## 二、三原则（李彦宏 2026-11-12 百度世界）

| 原则 | 原文 | 落地成什么 |
|---|---|---|
| **打破岗位边界** | 岗位是工业时代的单元，任务是智能时代的单元 | 不把 agent 绑死在固定职责上，按任务调度 |
| **沉淀隐性知识** | 个人经验显性化并沉淀到平台，才构成组织智能 | 建 `handbook/`，每个坑写成规则 |
| **设计流程闭环** | 「可衡量 + Looping = 持续进化」 | 每个 agent 有 KPI，失败必须回写规则 |

**⭐ 最有用的判断：** 如果一本手册删掉后组织照常运转，它还没形成组织智能。

## 三、四件套：任何一个 agent 必须有的四个属性

**缺任何一个，这个 agent 就是管理黑洞。**

```yaml
- name: xxx
  role: "English Role / 中文名"                          # ① 它是谁
  reports_to: vigiliae                                   # ② 向谁负责
  boundaries:                                            # ③ 它能做什么
    allow: ["read data", "append record"]
    deny: ["delete records", "publish externally"]
  kpi:                                                   # ④ 怎么判断干得好
    primary: "每轮新增多少条有效记录"
    fail: "采集的全是重复 / 抓不到源"
```

### ① role — 一个 agent 一个职责

**反面**：`role: "数据处理"` —— 太宽，等于没说
**正面**：`role: "Data Ingestor / 入库"` —— 明确到「校验 candidates.jsonl 后写 data.json」

### ② reports_to — 出了事能找到谁

**判据**：故障时能不能在一跳内找到负责人。
**如果 reports_to 是 `human`**，那这个 agent 就是直接对人负责，不能太多（更柝是 8 个，已经偏多）。

### ③ boundaries — 用 allow/deny 双向定义

**只写 allow 不够。** deny 才是防线：

```yaml
allow: ["read candidates", "validate", "append to data.json"]
deny: ["modify existing records", "delete records", "skip validation"]
```

### ④ kpi — 不是运行次数

**反面**：`runs: 9526` —— 只能证明它没死
**正面**：`primary: "状态切换是否被完整捕获（切换次数 = 报告次数）"`

## 四、分层：不要把所有 agent 平铺

**更柝的四条线分类法：**

| 线 | 职责 | 判断标准 | 典型成员 |
|---|---|---|---|
| **总控** | 协调，不替人决策 | 总览是否指出真实阻塞 | 1 个（不能再多） |
| **业务线** | 造东西 | **造出了什么** | 采集 / 织网 / 内容 |
| **保障线** | 保质量 | **拦住了多少该拦的** | 验证 / 记录 / 锚定 |
| **守夜线** | 对接人与系统 | **该提醒时提醒到了没有** | 心跳 / 时钟 / 成本 / 投递 / 门卫 |
| **支撑线** | 成本/价格/入库 | **发现多少** | 经费 / 盯价 / 入库 |
| **服务节点** | 按需调用，不定时 | 问答准确率 | 领域 Master |

**⭐ 关键区分：`agent`（定时跑）vs `service`（按需调用）。**

**更柝踩过的坑**：6 个领域 Master 被注册成 agent，但 `runs = 0` —— 它们从来不跑。
正确做法是把它们标成 `service`，从调度里摘出去。

```yaml
# 错误：让它们参与定时调度，永远失败
kind: agent
schedule: "every:300"

# 正确：明确标为服务节点
kind: service
schedule: null
```

## 五、汇报分级：什么时候才该打扰人

**只有四种情况升级到人：**

| 情况 | 触发条件 |
|---|---|
| **需要决策** | 涉及钱、签字、对外发布 |
| **连续失败** | 同一 agent 连续 3 次失败 |
| **越界** | agent 试图做权限外的事 |
| **重大发现** | 数据质量 / 竞品 / 政策的重大变化 |

**其余全部自己处理。**

**⭐ 汇报格式（四行，不要更多）：**

```
· 谁在岗
· 什么被卡住
· 下一个动作（一句）
· 需要人做的（最多一条）
```

## 六、权限矩阵：一条铁律

> **Agent 可以「造」和「验」，不能「删」和「承诺」。**

| 能力 | Agent 自主 | 需审批 | 人专属 |
|---|:---:|:---:|:---:|
| 读数据 | ✅ | | |
| 写数据（追加） | ✅ | | |
| 改已有记录 | | ✅ | |
| 删除数据 | | | ✅ |
| 对外发布 | | | ✅ |
| 提交申报 | | | ✅ |
| 花钱 | | | ✅ |
| 改代码/配置 | | ✅ | |
| 代表公司承诺 | | | ✅ |

**为什么这条最重要**：agent 能造能验，错了可以回滚；一旦能删能承诺，错误不可逆。

## 七、三个闭环

**每个闭环都要有「可衡量」的指标，否则不是闭环是循环。**

### 数据闭环
```
采集 → 验证 → 入库 → 展示 → 发现问题 → 回去采集
```
指标：A 级占比、可追溯率、A 级无 URL 数

### 任务闭环
```
创建 → 派单 → 执行 → 汇报 → 完成 → 归档
```
指标：完成率、平均处理时长、阻塞数

### 组织闭环
```
运行 → 记录 → 复盘 → 改规则 → 再运行
```
指标：**同类错误复发次数**

**⭐ 复发次数是唯一能证明「组织在变聪明」的指标。**
更柝 2026-11-15 时 C-067 类错误复发 6 次 —— 说明知识没沉淀，还在靠个人记忆。

## 八、组织手册：隐性知识怎么沉淀

**目录结构：**

```
handbook/
  README.md        # 章程 + 踩过的坑 + 数据规范 + 执行器限制
```

**每条坑的格式（必须四段）：**

```markdown
### R-01 · 标题 ⭐ 复发 N 次

**C-xxx**：具体犯了什么错

**规则**：以后遇到同类情况执行什么动作

**判断依据**：怎么确认你真的执行了（命令/检查项）
```

**⭐ 升级机制：**

| 复发次数 | 规则强度 |
|---|---|
| 1 次 | 「注意 X」 |
| **≥2 次** | **必须升级成「执行 Y 命令」，不能只是提醒** |

**更柝实例**：C-067「只看局部字段就下结论」复发到第 6 次，规则才升级成
「写检查脚本前必须先 `json.dumps(record, indent=1)` 打印 2–3 条完整记录」。

## 九、实施顺序（按依赖关系，不能跳）

```
第 1 步  对齐：yaml 定义数 == DB 注册数
           ↓
第 2 步  补 role/description（每个 agent 说清是谁）
           ↓
第 3 步  补 reports_to（建汇报树，不能有孤儿）
           ↓
第 4 步  补 boundaries（每个 agent 能做什么/不能做什么）
           ↓
第 5 步  补 kpi（怎么判断干得好）
           ↓
第 6 步  分层（agent vs service，不定时的摘出去）
           ↓
第 7 步  建 handbook（沉淀规则）
           ↓
第 8 步  做组织视图（可视化，让人一眼看到结构）
```

**⭐ 不要从第 8 步开始。** 先做可视化、结构是错的，只是把错误画得更清楚。

## 十、验收清单

改造完成后，逐条跑：

```python
# ① 定义与注册一致
len(yaml_agents) == db_task_count

# ② 无孤儿
all(a['reports_to'] for a in agents)

# ③ 无裸奔
all(a['boundaries'] for a in agents)

# ④ 全部可衡量
all(a['kpi'].get('primary') for a in agents)

# ⑤ 服务节点已摘出调度
all(not a.get('schedule') for a in agents if a['kind'] == 'service')

# ⑥ 手册存在且含至少 5 条规则
len(handbook_rules) >= 5
```

**更柝 2026-11-15 改造后：①–⑥ 全部通过，21/21。**

## 反面案例（真实踩过的）

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 只改 yaml，不同步 DB | 定义 12 个，实际跑 21 个，9 个裸奔 | 改完必须校验 `yaml 数 == DB 数` |
| 把所有节点都标成 agent | 6 个领域 Master `runs=0`，永远「未运行」 | 按需调用的标 `service`，`schedule: null` |
| 只写 allow 不写 deny | agent 能做权限外的事且不被拦 | deny 是防线，必须双向写 |
| KPI 用运行次数 | 9526 次运行，但不知道有没有用 | KPI 必须是「产出质量」不是「活动量」 |
| 先做可视化 | 把错误的结构画得很漂亮 | 先正结构，再可视化 |
| 手册只写「注意 X」 | 复发 6 次 | 复发 ≥2 次升级成「执行 Y 命令」 |
