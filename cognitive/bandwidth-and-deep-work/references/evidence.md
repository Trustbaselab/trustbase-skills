# 实证记录：这本书的规则在我们的项目里被验证过（evidence）

> 用途：当 `bandwidth-and-deep-work` skill 需要「这不是读书笔记，而是验证过的行为准则」的证据时加载。
> 口径来源：[trustbase/SKILL-PATCH-BRIEF.md](../../../trustbase/SKILL-PATCH-BRIEF.md)（DSH 战略侧补丁规格）与 [trustbase/REVIEW-TASK-TRACKING.md](../../../trustbase/REVIEW-TASK-TRACKING.md)（DSH 实测自查，2026-10-18）。
> ⚠️ 数据口径说明：SKILL-PATCH-BRIEF 记 DSH-INBOX.md 为 10,612 行；REVIEW-TASK-TRACKING 实测为 7,451 行。两处行数不一致，下方保留各自出处原文数字，不合并加工。

---

## 场景

一个 AI 驱动的项目组（Trustbase Lab），3 条自动化执行线，每天约 10–15 轮执行。每轮由一个 agent 执行方读取任务单、执行、写回执。

---

## 证据 1 · 任务单归档（应用《稀缺》：带宽税 → 释放带宽 + 余闲）

| 项 | 内容 |
|---|---|
| **问题** | 任务单 `DSH-INBOX.md` 只增不归档，膨胀到 **565.6 KB**（REVIEW 实测 7,451 行 / 353,705 字符 ≈ **141,500 tokens**；BRIEF 另记 10,612 行）；其中 **67 处 `STATUS: PENDING`** 绝大多数实际已完成 |
| **书里哪个概念** | **带宽税（bandwidth tax）**：历史任务单是「打开着的承诺」，执行方每轮都要读它找「当前任务」——这是对每轮执行征收的带宽税；**余闲（slack）**：没有归档机制，队列永远被历史占满 |
| **具体做法** | 按月/按任务归档：`DSH-INBOX.md` 只保留**当前队列 + 最近 3 轮**，历史移入 `_archive/`（如 `inbox-2026-10.md`） |
| **量化结果（前 → 后）** | 文件 **565.6 KB → 26.8 KB（-95%）**；PENDING **67 → 2**；执行方每轮读取 **≈141K → 5.6K tokens（-96%）**；不再因读到陈旧 PENDING 而做错任务（此前多次发生） |

> 对应《稀缺》原理：稀缺会自动俘获注意力——执行方被「找当前任务」这件本不该存在的工作反复征税。解法不是让执行方「更仔细」，而是**把历史移出带宽**（归档=外部化），让工作记忆只保留当前队列。

## 证据 2 · 单一真相源 status.json（应用《稀缺》：减少权衡式思维；《深度工作》：压缩浅层）

| 项 | 内容 |
|---|---|
| **问题** | 同一事实有 **4 个分散的状态来源**（`automations` 表、`automation_runs` 表、回执文本、看板），每次查状态要写 10–20 行 SQL + 读回执 + 看看板，**每次 2–3 分钟**，每天 10+ 次 |
| **书里哪个概念** | **权衡式思维（trade-off thinking）**：交叉核对 4 个来源 = 持续的小决策与小权衡，累积成带宽税；**浅层工作（shallow work）**：状态查询是后勤型浅层工作，应压缩到一次读 |
| **具体做法** | 由看板脚本生成 `status.json`（三线状态 + 队列 + 告警），**一次 `read` 即完成查询** |
| **量化结果（前 → 后）** | 状态查询 **2–3 分钟 → 5 秒**；当前文件实测 **2.5 KB**（`trustbase/_monitor/status.json`，2,560 字节） |

## 证据 3 · 默认沉默 + 一天一个深度块（应用《深度工作》：缩减浅层 + 深块）

| 项 | 内容 |
|---|---|
| **问题** | 执行方每轮写长报告、并行接多个任务；主线 30 轮失败 6 次（**20% 失败率**），失败原因含「任务过重」「同时做多件」「外部中断」 |
| **书里哪个概念** | **Drain the Shallows（摒弃浮浅）**：无变化不写长报告——回执只写增量；**深块 + 防杂耍**：一天只做一个深度块（其余任务搁置）、强制「一轮一件」+ 25 分钟自检点 |
| **具体做法** | 默认沉默协议（无变化 → 极简回执）；每日单一深块排程；失败原因分类统计 |
| **量化结果（前 → 后）** | 主线失败率 20% → 目标 5%（改造进行中，REVIEW 记录基线为 30 轮失败 6 次）；不再做错任务（BRIEF 结论） |

> 对应《深度工作》原理：浅层工作必须被**计量、批处理、压缩**；回执写增量而非复述，就是把「浅层通胀」排掉。失败率改造对应「一次一事 + 深块」——杂耍（多线程腾挪）正是失败的结构性原因。

## 数据口径与诚实边界

1. 行数口径不一致：BRIEF（10,612 行）vs REVIEW-TASK-TRACKING（7,451 行）。未合并，两处照录。
2. token 数均为估算（字符数 ÷ 2.5 或按读取比例推算），REVIEW 原文标注「只能估算」。
3. 「5.6K/轮」「不再做错任务」「失败率 5%」来自 BRIEF 与改造目标记录；失败率改造仍在进行中，尚未看到收敛后的完整统计。
4. 应用归因：归档与 status.json 是工程手段，与书概念的对应是**事后映射**（先有改造，后有概念归因），不是对照实验——引用时表述为「本项目的验证案例」，而非「因果证明」。
